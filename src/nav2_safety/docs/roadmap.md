# 后续改进清单

安全层只补了"运动指令"这一层。下面是其余待办，按**我建议的先后顺序**排，
附具体依据。

排序考虑了两件事：一是底盘自带的 500ms 通讯保护已经覆盖了什么（它让一部分
"停车"类需求不再是缺口），二是哪些问题在实机上最容易真的咬到你。

## 0. 网页/rosbridge 鉴权 —— 已决定不做（记录在案）

`web_start.sh` 让 rosbridge 监听 `0.0.0.0:9090`，网页没有认证，局域网内任何人都能
发导航目标、遥控，也能按下或**解除**急停。

**这是有意识的取舍，不是遗漏**：当前是自用/实验场景，加认证会明显增加使用成本
（每次连页面都要带凭据、TLS 证书管理），而你更看重"随手就能连上"。
记录在这里是为了将来要演示、外借或上产线时能立刻翻到。

到时候要补的话，方向是：rosbridge 只监听内网网段 + `authenticate`（或前置带认证的
反向代理）+ TLS。另外建议把"解除急停"做成比"能连网页"更高的权限 —— 否则误触就
能把别人刚锁死的车放行。

## 3. 负障碍 / 低矮障碍的盲区

`Pointcloud2d_3d.yaml` 的切片高度带是 0.2–1.0 m，所以**20cm 以下的障碍、坑洞、
下台阶在代价地图上完全不存在**，也没有悬崖检测。

这一条不受底盘 500ms 保护的任何帮助——它是"压根看不见"，不是"看见了没刹住"，
属于真正的安全缺口。

你车上有 RealSense D456/D405 和 Orbbec Gemini，URDF 里挂着，但整条导航链**一个
像素都没用**。深度相机做地面分割 / 负障碍检测是这里最直接的补法。


## 4. 地图质量：回环检测

FAST-LIO 单跑没有回环，长距离建图必然累积漂移，地图越走越歪。方案：在 LIO 外面
套位姿图（GTSAM），或换 MOLA / LIO-SAM。这是大场景能否成立的瓶颈——
如果你只在几十米的室内跑，优先级可以往后放。

另外 2D 栅格图来自 `slam_toolbox`、3D 先验图来自 FAST-LIO，不是同一次建图就会
错位（原 README 排障里就有这条）。理想做法是两者从同一来源生成。

## 5. 里程计融合 —— 核查结论：**建议不做**，理由是它很可能让定位变差

原以为"LIO 是唯一里程计来源、轮式里程计没人用"是个缺口。核查之后这个判断站不住：

1. **IMU 已经被融合了。** FAST-LIO 是紧耦合的 LiDAR-IMU 里程计
   （`config/mid360.yaml` 里 `imu_topic: /livox/imu`），再加一个 `robot_localization`
   的 EKF 去融 IMU 属于重复计入同一个信息源。
2. **轮式里程计在这台车上质量偏差。** 滑移转向原地转向时车轮必然打滑，而本车
   `wz_max = 1.0 rad/s`、又常做原地转向（重定位、对目标朝向），轮速积分出来的
   航向误差会很大。用一个较差的源去"融合"较好的源，除非把权重压得很低，
   否则结果是变差。
3. **LIO 真正的短板不是"没有融合"，而是"没有绝对参考"。** 长时漂移这件事
   已经由重定位（`map -> odom`）解决了，那才是对应手段，不是 EKF。
4. **还多一个依赖**：`robot_localization` 当前未安装。

真要用上 `/wheel_odom`，唯一站得住的做法是**当诊断交叉校验、不当融合输入**：
   比如"指令在动、轮速也为 0、LIO 却说在移动"这类组合才判可疑。但它阈值宽、
   误报会直接锁掉自动驾驶（可用性问题），而现有 `tracking_ok` + TF 新鲜度已经
   覆盖了现实的失效模式。**所以也不建议做**，除非将来真的观测到"LIO 报了错误的
   运动"而 `tracking_ok` 没抓到——那时再针对性加。

结论：这一条从待办里移除。原来的判断是我基于"有人发没人收"的表面现象得出的，
没有先验证两者的信息是否重复。

## 6. 导航质量调优 —— 已完成 DWB→MPPI、NavFn→Smac

- [x] **DWB → MPPI**（`nav2_mppi_controller::MPPIController`）：参数按本车限制适配
      （vx/wz 与 velocity_smoother 一致），并开了 `ObstaclesCritic.consider_footprint`
      —— 本车轮廓是 0.69×0.57 的矩形，关掉的话只按中心点判碰撞，会低估车角扫过的区域。
- [x] **NavFn → Smac 2D**（`nav2_smac_planner/SmacPlanner2D`）：选 2D 而不是 Hybrid/Lattice，
      因为它是 NavFn 的直接替换、不需要标定最小转弯半径。`allow_unknown` 保持原行为
      （true），配置里写明了它在未建图区域没有依据。
- [x] **`smoother_server` 死配置**：已加详细注释说明它不被默认行为树调用、为什么先留着
      不删（共享配置，删了有让回滚路径激活失败的风险）。换成 MPPI 后平滑的意义也更小了。
- [ ] **分区限速 / 禁行区**：`KeepoutFilter`、`SpeedFilter` 仍未配。这个需要你先定义
      禁行区/限速区的掩膜图，属于"有需求才做"，我没有凭空造一个占位掩膜。

### 验证

整栈用真实地图 + 伪 TF/点云起起来，6 个生命周期节点全部 `active`，日志确认插件
确实换成了 `nav2_mppi_controller::MPPIController` 与 `nav2_smac_planner/SmacPlanner2D`。

过程中发现并修掉一个**真的安全漏洞**：`behavior_server`（spin/backup/drive_on_heading
等恢复行为）默认直接发布 `/cmd_vel`，会整条绕过安全链——急停锁不住它、
`collision_monitor` 也管不到它。已在安全版启动文件里把它重映射进导航指令流。
这个问题是 `cmd_vel_deadman` 的"外来发布者自检"报出来的。

### 一个顺手发现的坑

`me_nav2_bringup` 的 `config/` 在 install 目录里是**拷贝而不是符号链接**，所以
**改 `nav2_params.yaml` 必须重新编译才生效**（我这次就是先被日志里的
`NavfnPlanner` 提醒才发现前面几轮的参数改动从未生效）。对比之下 `map_config.yaml`
能即时生效，是因为 launch 里为它单独写了"优先读源码目录"的逻辑。建议要么把
`nav2_params.yaml` 也纳入这个机制，要么在文档里把这条写清楚。
